# TeensyROM+ integration: how it works

Implementation notes for the firmware side. Installing and using the result is described in the [top-level README](../README.md).
The patch (`teensyrom-vdrive.patch`, generated by `tools/make_tr_patch.sh`) adds `Fab04_VDrive` (enabled next to `Fab04_KernalReplace` in
`Common_Defs.h`), `VDrive_Agent` and `VDrive_Any` (both boards; the agent, below), the Special IOs `IOH_VDrive` ("VDrive KERNAL"), `IOH_VDriveSwift` ("VDrive+SwiftLink") and `IOH_VDriveSwiftREU` ("VDrive+Swift+REU"), `IOH_VDriveREU` ("VDrive+REU"), the library under
`MinimalBoot/Common/vdrive/` (with `vd_kpatch.h`, the KERNAL patches as a table from `tools/build.py --table`; the D64/D71/D81 engine is the
tree's own `Source/Teensy/DiskImage`, which `IOH_VDrive.c` includes through `DiskImage.h`), and a few lines in
`KERNALPreStart()` and `InitHndlr_KERNALReplace_PreStart()` so the VDrive Special IOs serve their own KERNAL image.

## The KERNAL image
`KERNALPreStart()` sets `KernalImageSource` (new in `IOH_KernalReplace.c`) to `VD_KernalImage` for a VDrive Special IO and to NULL for Kernal
Replace; `InitHndlr_KERNALReplace_PreStart()` then fills `KernalBin` from that function instead of the `<Shift-K>` file. `VD_KernalImage`
(`IOH_VDrive.c`) takes `/VDrive/kernal.bin` from the SD card when it is there (8192 bytes, as it is), else reads `$E000-$FFFF` by DMA, checks
the CRC-32 against `VD_KnownKernals` and lays `VD_KernalPatch` over it; anything else serves nothing (the C64's own KERNAL, drives off).
An image that already holds every run of `VD_KernalPatch` (`VD_KernalPatchPresent`: this build's KERNAL in an EPROM or a MEGA65 core) also
serves nothing, but its drives work: the mailbox is live whatever is served. Only a served image or that one gets the menu's bus probe
(`vdNoMenuProbe`); docs/DESIGN.md section 45.
When a VDrive Special IO runs, the KERNAL's cold start (`SYS64738`) sends `VIO_MENU` after reading the ID registers `$DE19/$DE1A` (`$D6 $64`).
`docs/DESIGN.md` section 40.

## VDrive+SwiftLink
`IOH_VDriveSwift.c` runs the virtual drive and the SwiftLink / Turbo232 modem together: IO1 `$DE00-$DE0F` goes to the
SwiftLink handler, `$DE10-$DE1A` to the drive mailbox (this is why the mailbox moved off `$DE00`), IO2 `$DF80-$DFFF` to the drive window, the per-cycle
callback to SwiftLink, and init/polling run both. When the default Special IO (EEPROM) is VDrive or VDrive+SwiftLink, a built-in menu program
paired with plain SwiftLink is started with this handler instead (`VDriveSwift_Remap()` in `KERNALPreStart()` and `IOHandlerSelectInit()`).

## VDrive+REU
`IOH_VDriveREU.c` runs the virtual drive and the REU (`IOH_REU.c`, unchanged): IO1 `$DE10-$DE1A` is the drive mailbox, IO2 `$DF00-$DF7F` the
REU registers, `$DF80-$DFFF` the drive window, no per-cycle callback. Init runs the REU (the 128 KB RAM1 image plus 384 KB of RAM2: the full
512 KB, as the plain REU handler; the drive keeps no data in RAM2, which would shrink that heap, `docs/DESIGN.md` 50) and then VDrive. The REU's `$FF00` trigger would take over `fBusSnoop`, which serves the KERNAL; the IO2
handler (`IO2Hndlr_VDriveREU`, also used by VDrive+Swift+REU) hands it back (`VDREU_Snoop`). With any VDrive Special IO as the default, menu
programs paired with the REU start with this handler. `docs/DESIGN.md` section 34.

## VDrive+Swift+REU
`IOH_VDriveSwiftREU.c` adds SwiftLink to VDrive+REU (it shares its IO2 handler): IO2 `$DF00-$DF7F` goes to the REU registers, `$DF80-$DFFF` to the
drive window. Init runs SwiftLink, then the REU (it takes the free 128 KB RAM1 image and what RAM2 is left, rounded down to a power of two), then VDrive.
The REU's `$FF00` trigger would take over `fBusSnoop`, which serves the KERNAL; the IO2 handler hands it back (`VDREU_Snoop`). Details and
what is untested: `docs/DESIGN.md` section 32.

## The agent: "VDrive" on the plain TeensyROM, "VDrive Agent" on the TR+
`IOH_VDriveAgent.c` (gate `VDrive_Agent`, both boards) needs no Kernal Replace. The C64 keeps its own KERNAL; its RAM vectors point into a
246-byte 6502 agent (`vector/vdagent.s`, `vdrive/vd_agent.h`) served from a RAM1 page at IO1 `$DE08-$DEFF`. The page keeps the agent's own
writes and is refreshed at init. The mailbox registers are at IO2 `$DF00-$DF0A` and the window at `$DF80`. The vector engine
(`vdrive/vdrive_vec.c`, `vvec_poll`) answers it, on the same drive and SD/USB glue as the KERNAL handlers (`IOH_VDrive.c`: shared parts under
`VDrive_Any`, KERNAL parts under `Fab04_VDrive`).

- `KERNALPreStart()` calls `VDrive_AgentPreStart()` first, which runs the drive's PreStart and skips the KERNAL load.
- The menu's PRG loader calls the agent's INSTALL entry (`$DE14`) once the program is in memory, if the ID `$D6 $64` answers at `$DF09/$DF0A`.
- After a reset, `SYS 56852` hooks the vectors again.
- **C128 in 128 mode** (0.9.0.62, VICE only): upstream's `LaunchC128BasicPrg()` (`C128Prg.ino`) calls `VDrive_C128Launch()`, which with any
  VDrive Special IO as the default sets the agent for that launch and runs the drive's PreStart; the C128 boot ROM's loader
  (`C128PrgBoot.asm`) calls INSTALL before it types RUN. The engine tells the C128's KERNAL from the C64's at INSTALL (`$FFD5`).
  Since 0.9.0.63 Exit to C128 BASIC goes through the boot ROM too when `VDrive_C128Launch()` chose the agent (no RUN typed for it).
  Since 0.9.0.65 that INSTALL also writes the drives into BASIC 7's start-up message (` ALL RIGHTS RESERVED  VDRIVE SD 8 USB 9`), after the bus scan.
  Since 0.9.0.66 the C64 launch INSTALL (`PRGLoadStartReloc.s`) does the same for the C64 banner's second line (` 64K RAM  38911 FREE  VDRIVE SD 8 USB 9`).
- **Alt button under the agent** (TR+, 0.9.0.63): `InitHndlr_VDriveAgent()` wires disk switching; the border flash is `VD_BorderDMA()`
  (in `IOH_VDrive.c`, shared with the KERNAL handlers since 0.9.0.64), one `HoldC64()` per step, `$D020` written only when `$D020-$D03F` read as the VIC.

`docs/DESIGN.md` sections 52-57.

## Device numbers
`pin[]` (user, two EEPROM bytes `eepAdVDriveDevs`; 0 or an invalid value = automatic) and `dev[]` (current, 0 = none). Build-time defaults of the
automatic numbers are `VD_DEV0`/`VD_DEV1` in `d64/vd_cfg.h`; `vdrive_set_devices()` is the C API. The EEPROM bytes are carved out of the reserved
area (`eepAdNext` moves from 4235 to 4237, reset-to-defaults zeroes them); `eepMagicNum` is not bumped because 0/0xFF/garbage all mean automatic.

## Remote control
`VDrive_RemoteStatus` / `VDrive_RemoteSet` in `IOH_VDrive.c` implement commands `0x64E3` / `0x64E4` on the TeensyROM remote-control port; the dispatcher text is
`vdrive_remote.inc`, inserted into `SerUSBIO.ino`. Framing and details are in `docs/DESIGN.md` section 20.
The Alt button disk switching (`SpecialBtn_VDrive`, `VD_SwitchNext`, `/vdrive-config.txt`, the border flash by DMA, `VD_BorderDMA`) is in the same file; see `docs/DESIGN.md` sections 22 and 58.

## What changed in the KERNAL (`patches/vdrive.s`)
* The 8 serial entry points (`LISTEN TALK SECOND TKSA CIOUT ACPTR UNLSN UNTLK`) `JMP` into stubs that ask the mailbox
  whether the transaction is for one of the virtual drives; "not mine" replays the displaced instructions into the stock routine.
* `LOAD` (`$F4C8`) and `SAVE` (`$F605`) get block-transfer fast paths (any device is offered to the Teensy first; ~one extra mailbox round trip when the device is a real drive); `VERIFY` takes the stock path.
* The first LISTEN / TALK / LOAD / SAVE of a run may be answered with the token `$3C`: `vcall` then runs the bus scan (`bus_scan`, ~100 bytes) and repeats the command.
  Since 0.9.0.35 the TR menu probes the bus before the launch (`firmware/vdrive_probe.asm` in `MainMenu.asm`, docs/DESIGN.md 37), so this is only the fallback.
* The mailbox answer is a token (`$5A` / `$A5`); a bad or missing answer in the middle of a transfer aborts it with an error. Before any mailbox write `vcall` checks the ID register `$DE19` (`vd_here`, 4 tries); without a VDrive handler every call goes to the stock IEC code at once and nothing is written to IO1/IO2, so the image is harmless in a ROM socket, with another Special IO and under the TR menu (since 0.9.0.48; before, a ~1 s time-out per call). A handler that does not answer still falls back after the ~1 s time-out.
* Space comes from the cassette bit-timing code `$F8E2-$FB8D`: **tape I/O (device 1) no longer works.**


Build with `-DVD_TRACE` for a per-command serial trace; it is off by default because the printing makes the bus handler answer late.

Uncomment `#define LATE_ISR_TRACE` in `Common_Defs.h` (after the patch is applied) to count late phi2 interrupts (`ISRs.c`) and print them on the serial console: `LATE-ISR ...` at most every 2 s, and for the first 20 s after each Kernal Replace/VDrive launch a `TRACE +ms ...` line every 250 ms with the counters, the PIT/ENET interrupt state and whether `loop()` polls the Ethernet stack. Off by default: nothing of it is compiled in. `#define KERNAL_NO_DTCM` (`IOH_KernalReplace.c`) serves the image from the malloc'ed `KernalBin` instead of the 8 KB RAM1 copy `KernalFast`.

## What is and isn't verified
Host (`make test`): the D64 / D71 / D81 engine against `c1541` (contents, BAM equality with `c1541 -validate`, formats), the bus scan in VICE with
true-drive 1541s at 8 and 10 (the SD drive lands on 9, the USB drive on 11), the register-level engine, the 6502 patches in VICE (via a RAM mailbox +
monitor-driven mock), and `IOH_VDrive.c` compiled as C++ with `-Wall -Wextra -Werror` against host stubs of the Teensy/TeensyROM API, driving real
files through the IO1/IO2 entry points.

Hardware (real C64, TR+, SD and USB): the core drive path, device numbers (`U0>`, EEPROM), paths, auto-mount and remembered mounts, VDrive+SwiftLink,
and remote get/set, `trls` and image swap while a program runs. The status list is in `CLAUDE.md`.

**Not yet checked on hardware:** the bus scan with a real 1541 on the bus (it assumes the VDrive handler is not yet active during BASIC init, and that real
drives behave like VICE's emulation), `.d81` mounting on the card, `.d71` at all, `STATUS` compared with a real drive, and IRQ/STOP-key interplay during loads.
