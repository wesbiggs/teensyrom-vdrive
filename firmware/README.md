# TeensyROM+ integration: how it works

Implementation notes for the firmware side. Installing and using the result is described in the [top-level README](../README.md).
The patch (`teensyrom-tdrive.patch`, generated by `tools/make_tr_patch.sh`) adds `Fab04_TDrive` (enabled next to `Fab04_KernalReplace` in
`Common_Defs.h`), `TDrive_Agent` and `TDrive_Any` (both boards; the agent, below), the Special IOs `IOH_TDrive` ("TDrive KERNAL"), `IOH_TDriveSwift` ("TDrive+SwiftLink") and `IOH_TDriveSwiftREU` ("TDrive+Swift+REU"), `IOH_TDriveREU` ("TDrive+REU") on the TR+ and
`IOH_TDriveAgent` ("TDrive" on the plain TR, "TDrive Agent" on the TR+), the library under
`MinimalBoot/Common/tdrive/` (with `vd_kpatch.h`, the KERNAL patches as a table from `tools/build.py --table`, and `vd_agent.h`, the agent from
`tools/build_agent.py`; the D64/D71/D81 engine is the tree's own `Source/Teensy/DiskImage`, which `IOH_TDrive.c` includes through `DiskImage.h`), and
edits to upstream files: `KERNALPreStart()` and `InitHndlr_KERNALReplace_PreStart()` so the TDrive Special IOs serve their own KERNAL image
(and the agent runs its PreStart), the remote commands and the `trls` exception in `SerUSBIO.ino`, the EEPROM bytes `eepAdTDriveDevs`, the
menu's launch-time bus probe (`MainMenu.asm`), the agent's INSTALL call in the menu's PRG loader and the C128 boot ROM, TDrive Config in the
menu's Utilities (`vdconfig.prg.h`), and the SwiftLink / REU remap (`TDriveSwift_Remap()`). `tools/make_tr_patch.sh` lists every edit.

## The KERNAL image
`KERNALPreStart()` sets `KernalImageSource` (new in `IOH_KernalReplace.c`) to `VD_KernalImage` for a TDrive Special IO and to NULL for Kernal
Replace; `InitHndlr_KERNALReplace_PreStart()` then fills `KernalBin` from that function instead of the `<Shift-K>` file. `VD_KernalImage`
(`IOH_TDrive.c`) takes `/TDrive/kernal.bin` from the SD card when it is there (8192 bytes, as it is), else reads `$E000-$FFFF` by DMA, checks
the CRC-32 against `VD_KnownKernals` and lays `VD_KernalPatch` over it; anything else serves nothing (the C64's own KERNAL, drives off).
An image that already holds every run of `VD_KernalPatch` (`VD_KernalPatchPresent`: this build's KERNAL in an EPROM or a MEGA65 core) also
serves nothing, but its drives work: the mailbox is live whatever is served. Only a served image or that one gets the menu's bus probe
(`vdNoMenuProbe`); docs/DESIGN.md section 45.
When a TDrive Special IO runs, the KERNAL's cold start (`SYS64738`) sends `VIO_MENU` after reading the ID registers `$DE19/$DE1A` (`$D6 $64`).
`docs/DESIGN.md` section 40.

## TDrive+SwiftLink
`IOH_TDriveSwift.c` runs the virtual drive and the SwiftLink / Turbo232 modem together: IO1 `$DE00-$DE0F` goes to the
SwiftLink handler, `$DE10-$DE1A` to the drive mailbox (this is why the mailbox moved off `$DE00`), IO2 `$DF80-$DFFF` to the drive window, the per-cycle
callback to SwiftLink, and init/polling run both. When the default Special IO (EEPROM) is TDrive KERNAL, TDrive+SwiftLink or TDrive+REU, a
built-in menu program paired with plain SwiftLink is started with this handler instead (with TDrive+Swift+REU as the default, with that one;
`TDriveSwift_Remap()` in `KERNALPreStart()` and `IOHandlerSelectInit()`). With TDrive Agent as the default there is no combined handler: such a
program runs with plain SwiftLink and without the drives.

## TDrive+REU
`IOH_TDriveREU.c` runs the virtual drive and the REU (`IOH_REU.c`, unchanged): IO1 `$DE10-$DE1A` is the drive mailbox, IO2 `$DF00-$DF7F` the
REU registers, `$DF80-$DFFF` the drive window, no per-cycle callback. Init runs the REU (the 128 KB RAM1 image plus 384 KB of RAM2: the full
512 KB, as the plain REU handler; the drive keeps no data in RAM2, which would shrink that heap, `docs/DESIGN.md` 50) and then TDrive. The REU's `$FF00` trigger would take over `fBusSnoop`, which serves the KERNAL; the IO2
handler (`IO2Hndlr_TDriveREU`, also used by TDrive+Swift+REU) hands it back (`VDREU_Snoop`). With any TDrive KERNAL Special IO as the default (not
TDrive Agent), menu programs paired with the REU start with this handler. `docs/DESIGN.md` section 34.

## TDrive+Swift+REU
`IOH_TDriveSwiftREU.c` adds SwiftLink to TDrive+REU (it shares its IO2 handler): IO2 `$DF00-$DF7F` goes to the REU registers, `$DF80-$DFFF` to the
drive window. Init runs SwiftLink, then the REU (it takes the free 128 KB RAM1 image and what RAM2 is left, rounded down to a power of two), then TDrive.
The REU's `$FF00` trigger would take over `fBusSnoop`, which serves the KERNAL; the IO2 handler hands it back (`VDREU_Snoop`). Details and
what is untested: `docs/DESIGN.md` section 32.

## The agent: "TDrive" on the plain TeensyROM, "TDrive Agent" on the TR+
`IOH_TDriveAgent.c` (gate `TDrive_Agent`, both boards) needs no Kernal Replace. The C64 keeps its own KERNAL; its RAM vectors point into a
246-byte 6502 agent (`vector/vdagent.s`, `tdrive/vd_agent.h`) served from a RAM1 page at IO1 `$DE08-$DEFF`. The page keeps the agent's own
writes and is refreshed at init. The mailbox registers are at IO2 `$DF00-$DF0A` and the window at `$DF80`. The vector engine
(`tdrive/tdrive_vec.c`, `vvec_poll`) answers it, on the same drive and SD/USB glue as the KERNAL handlers (`IOH_TDrive.c`: shared parts under
`TDrive_Any`, KERNAL parts under `Fab04_TDrive`).

- `KERNALPreStart()` calls `TDrive_AgentPreStart()` first, which runs the drive's PreStart and skips the KERNAL load.
- The menu's PRG loader calls the agent's INSTALL entry (`$DE14`) once the program is in memory, if the ID `$D6 $64` answers at `$DF09/$DF0A`.
- After a reset, `SYS 56852` hooks the vectors again.
- **C128 in 128 mode** (0.9.0.62, VICE only): upstream's `LaunchC128BasicPrg()` (`C128Prg.ino`) calls `TDrive_C128Launch()`, which with any
  TDrive Special IO as the default sets the agent for that launch and runs the drive's PreStart; the C128 boot ROM's loader
  (`C128PrgBoot.asm`) calls INSTALL before it types RUN. The engine tells the C128's KERNAL from the C64's at INSTALL (`$FFD5`).
  Since 0.9.0.63 Exit to C128 BASIC goes through the boot ROM too when `TDrive_C128Launch()` chose the agent (no RUN typed for it).
  Since 0.9.0.65 that INSTALL also writes the drives into BASIC 7's start-up message (` ALL RIGHTS RESERVED  TDRIVE SD 8 USB 9`), after the bus scan.
- **Alt button under the agent** (TR+, 0.9.0.63): `InitHndlr_TDriveAgent()` wires disk switching, without a border flash since 0.9.0.66
  (0.9.0.63-0.9.0.65 flashed by DMA, `HoldC64()` per step, which crashed running programs on hardware; `docs/DESIGN.md` 60).

`docs/DESIGN.md` sections 52-57.

## Device numbers
`pin[]` (user, two EEPROM bytes `eepAdTDriveDevs`; 0 or an invalid value = automatic) and `dev[]` (current, 0 = none). Build-time defaults of the
automatic numbers are `VD_DEV0`/`VD_DEV1` in `d64/vd_cfg.h`; `tdrive_set_devices()` is the C API. The EEPROM bytes are carved out of the reserved
area (`eepAdNext` moves from 4235 to 4237, reset-to-defaults zeroes them); `eepMagicNum` is not bumped because 0/0xFF/garbage all mean automatic.

## Remote control
`TDrive_RemoteStatus` / `TDrive_RemoteSet` in `IOH_TDrive.c` implement commands `0x64E3` / `0x64E4` on the TeensyROM remote-control port; the dispatcher text is
`tdrive_remote.inc`, inserted into `SerUSBIO.ino`. Framing and details are in `docs/DESIGN.md` section 20.
The Alt button disk switching (`SpecialBtn_TDrive`, `VD_SwitchNext`, `/tdrive-config.txt`, the border flash through the `BORDER` register) is in the same file; see `docs/DESIGN.md` sections 22 and 60.

## What changed in the KERNAL (`patches/tdrive.s`)
* The 8 serial entry points (`LISTEN TALK SECOND TKSA CIOUT ACPTR UNLSN UNTLK`) `JMP` into stubs that ask the mailbox
  whether the transaction is for one of the virtual drives; "not mine" replays the displaced instructions into the stock routine.
* `LOAD` (`$F4C8`) and `SAVE` (`$F605`) get block-transfer fast paths (any device is offered to the Teensy first; ~one extra mailbox round trip when the device is a real drive):
  128-byte window blocks, or with the `-DMA` firmware parts of up to 2 KB that the Teensy writes into / reads from RAM by DMA (`VIO_FLOAD_DMA`, `VIO_FSAVE_DMA`;
  docs/DESIGN.md 49, 51). `VERIFY` is compared by the Teensy (`VIO_FVERIFY_OPEN`) when the firmware can read RAM by DMA and the whole file lies in
  `$0200-$CFFF`, else it takes the stock path through the hooked serial routines.
* The first LISTEN / TALK / LOAD / SAVE of a run may be answered with the token `$3C`: `vcall` then runs the bus scan (`bus_scan`, ~100 bytes) and repeats the command.
  Since 0.9.0.35 the TR menu probes the bus before the launch (`firmware/tdrive_probe.asm` in `MainMenu.asm`, docs/DESIGN.md 37), so this is only the fallback.
* The mailbox answer is a token (`$5A` / `$A5`); a bad or missing answer in the middle of a transfer aborts it with an error. Before any mailbox write `vcall` checks the ID register `$DE19` (`vd_here`, 4 tries); without a TDrive handler every call goes to the stock IEC code at once and nothing is written to IO1/IO2, so the image is harmless in a ROM socket, with another Special IO and under the TR menu (since 0.9.0.48; before, a ~1 s time-out per call). A handler that does not answer still falls back after the ~1 s time-out.
* Smaller hooks: the IRQ routine's border flash for the Alt button (`irq_border`, `$EA32`, the `BORDER` register `$DE18`), the cold start
  (`$FCE2`: `SYS64738` back to the TR menu), SHIFT+RUN/STOP (`$E5EE`: types `LOAD"*",8,1` and `RUN`), device 8 as the default for `LOAD`/`SAVE`/`VERIFY`
  (`$E1DA`), and the drive numbers in the power-on banner (`patches/vdbanner.s`, INITMS at `$E42D`/`$E43D`).
* Space comes from the cassette code: `$F8E2-$FB8D` (the serial hooks and fast paths), `$F875-$F8CF` (`rst_hook`, `shift_run`) and `$FB97-$FCD0`
  (the banner): **tape I/O (device 1) no longer works.**


Build with `-DVD_TRACE` for a per-command serial trace; it is off by default because the printing makes the bus handler answer late.

Uncomment `#define LATE_ISR_TRACE` in `Common_Defs.h` (after the patch is applied) to count late phi2 interrupts (`ISRs.c`) and print them on the serial console: `LATE-ISR ...` at most every 2 s, and for the first 20 s after each Kernal Replace/TDrive launch a `TRACE +ms ...` line every 250 ms with the counters, the PIT/ENET interrupt state and whether `loop()` polls the Ethernet stack. Off by default: nothing of it is compiled in. `#define KERNAL_NO_DTCM` (`IOH_KernalReplace.c`) serves the image from the malloc'ed `KernalBin` instead of the 8 KB RAM1 copy `KernalFast`.

## What is and isn't verified
Host (`make test`): the D64 / D71 / D81 engine against `c1541` (contents, BAM equality with `c1541 -validate`, formats), the bus scan in VICE with
true-drive 1541s at 8 and 10 (the SD drive lands on 9, the USB drive on 11), the register-level engine, the 6502 patches in VICE (via a RAM mailbox +
monitor-driven mock), and `IOH_TDrive.c` compiled as C++ with `-Wall -Wextra -Werror` against host stubs of the Teensy/TeensyROM API, driving real
files through the IO1/IO2 entry points.

Hardware (real C64, TR+, SD and USB): the core drive path, device numbers (`U0>`, EEPROM) and the automatic numbers with a real 1541 on the bus,
paths, `.d64` / `.d71` / `.d81` images (VDSUITE), auto-mount and remembered mounts, TDrive+SwiftLink, remote get/set, `trls` and image swap while a
program runs, the Alt button. The status list, with what is not on hardware yet, is in `CLAUDE.md`.

**Not yet checked on hardware** (among others): `STATUS` compared with a real drive, IRQ/STOP-key interplay during loads, DMA SAVE and VERIFY, the
agent (plain TR, TDrive Agent, C128 in 128 mode).
